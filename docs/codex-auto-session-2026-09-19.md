# Codex 自动会话与编码验收进度

## 已实现

新增 `utk codex` 开发预览入口。它检查 Codex 版本和现有订阅登录，启动或复用本地原生服务，并为新启动的 Codex 进程绑定以下设置：

- HTTP 请求、只读命令改写、MCP 原文查询共用一个随机会话标识。
- 原模型、推理设置和审批策略保留；不切换收费 API，不复制认证文件。
- 通过 Codex 本地 `hooks/list` 接口取得钩子定义哈希，只信任本次 UTK 钩子。已有用户钩子的信任状态保留，未审核钩子不会被自动批准。
- 只在本进程停用已识别的 Headroom `init hook ensure --profile init-user --marker headroom-init-codex` 钩子，避免其再次改写全局路由；不修改全局钩子文件。
- 未知或受管理策略约束的 Headroom 钩子会阻止自动接入，不使用全局跳过钩子信任选项。
- 钩子只改写已识别的简单只读 Git/搜索命令。管道、脚本、未知选项和可执行外部程序的搜索参数保持原样。
- 工具统计带有客户端、会话和工具调用关联标识；原始参数不落盘。

当前版本门槛为 Codex 0.138.0。API Key、未知提供商、其他版本、resume/fork 尚未开放自动会话路径。直接启动普通 `codex` 的现有接入方式保持原状。

## 编码任务

验收脚本增加 `--coding-task`：创建独立临时 Git 仓库，要求模型读取并恢复原文，修复整数向上取整函数，再运行测试并检查差异。

初始测试为 3 失败、4 通过。独立验收会核对函数确实变化、测试文件哈希不变、只修改目标文件，并重新运行全部 7 项测试。模型的成功声明不能替代这些证据。

## 真实运行结果及后续修复

第一次自动钩子编码任务使用 `gpt-5.6-luna`，消耗 3 次请求，未通过：钩子没有被信任，原文查询失败，目标代码未修复；同时检测到 Codex 配置字节变化。本机存在 Headroom 初始化钩子，UTK 没有尝试盲目覆盖还原用户配置。

失败报告保留在 `output/codex-luna-20260919/report-019.json`。此前 `report-016.json` 的手动包装命令链路成功结果仍然有效，但不能作为自动钩子编码验收证据。

随后补上精确哈希信任与进程级 Headroom 钩子隔离。修复后的真实 Codex 本地接口预检确认钩子已受信任、冲突钩子在本进程停用、原用户配置字节不变；预检不调用模型。

Windows 与 WSL Ubuntu 当前完整离线测试均通过 97 项。Windows 并行验证期间曾有一次完整运行报告失败，串行重跑通过；尚不能据此声明长期稳定性验收完成。

旧批次累计消耗 **19/20** 次，剩余 1 次不足以重新完成编码任务。修复后的真实编码验收尚未运行，等待新增请求预算，不将此项标记为通过。

## 使用边界

`utk codex --model gpt-5.6-luna` 可启动开发预览会话；目前仍需完成修复后的真实验收，不能声明自动接入正式支持。退出进程后，临时配置覆盖失效。原文仍只保存在守护进程内存中，不提供跨重启恢复。

钩子行为与信任字段依据 Codex 0.138.0 本机协议及官方配置结构：

- https://developers.openai.com/codex/hooks
- https://raw.githubusercontent.com/openai/codex/rust-v0.138.0/codex-rs/core/config.schema.json
